# Progress, goals and reuse: evidence changes rather than a fusion score

## What the new graph measures
The timeline classifies existing dated public milestones as a model design finding, an unresolved/not-passed scientific test, verification/reuse of existing work, or a website/tooling change. The vertical rows are categories, not a ranked maturity score. The graph does not add those events into a percentage or infer that a larger number of runs/tests/reports means a better reactor.

All previously published milestones in `project-status.json` from 7–16 September 2026 are covered, plus this interface update itself. This is a curated public milestone history, not a complete log of every action or the full earlier project archive. Older reports remain in the existing research library. Dates are the recorded study dates; within-day timestamps are not invented. Every event has linked repository evidence and a source-file hash.

Physical fusion and measured electricity remain not demonstrated/not measured for this project. Their absence is represented as a categorical status—not a flat numerical zero-power measurement. The most recent recorded candidate power study is 14 September. The subsequent 16 September scientific finding exposed a mismatch in the magnetic-equilibrium assumptions; it did not establish a new power output. Later usability/access changes belong in the tooling row, not the scientific-result row.

The existing `power-progress/` dashboard already provides the detailed model-power history, rejected claims, physical experiment context and source hashes. It is linked rather than rebuilt or reinterpreted as a physical progress curve. The homepage's new preview uses the same timeline component and packet as the detailed `progress/` page. The existing concept and `#watch` particle animation remain available.

## Roadmap and timing
The six goals are dependency-linked review checkpoints: candidate input readiness; consistent plasma/current equilibrium; heating/current-drive qualification; matched same-design cooling/fuel/material analysis; authorized physical validation; measured useful net electricity. The first four are numerical/evidence tasks, not equivalent-sized steps toward a power plant. The last two require resources, measurements and approvals that are not scheduled here.

The roadmap states a pass rule, a stop/revise rule, missing inputs, dependencies and existing methods for each goal. The established actuator target, approximately 7.598 MA within 170 MW credited drive, is necessary but not sufficient; required heating, control and current-profile behavior must also coexist. The exact constraint and rejection rule come from existing issue7 and the plant/actuator reports. The completed proxy-equilibrium mismatch is not proof the concept is impossible; it prevents silently qualifying a different plasma as the original design.

Past dates are factual. Future order is not a calendar commitment. No credible reactor-completion date, booked hardware experiment or continuously running agent is asserted. Input and prior-work review comes before another scientific run; a finite budget and numerical acceptance rules must then be frozen. Relevant benchmark-data review can proceed in parallel, but full engineering integration depends on the same qualified design, not a mixture of favorable cases. This update is a plan and presentation change, not completion of the planned calculations.

## Anti-redundancy enforcement and its limits
The roadmap reuses `research/prior_work_register.json`; it does not create a second bibliography or substitute a new generic solver. Redl et al.'s established self-generated-current model was already identified in issue7 and is added to the register for explicit goal linkage. The original-contributor summary and official TokaMaker bootstrap example were checked again before specifying this plan. No new bootstrap calculation was run and no novelty claim is made for the method.

`tools/build_progress_roadmap.py` rejects missing source files, unclassified new milestones, missing pass/stop criteria, unknown prior-work references and circular goal dependencies. `check_task_review` flags missing input readiness, unbounded run counts/timeouts, missing scientific review and an unchanged repeat without a named independent-verification gap. The stored next-task review is intentionally not ready: candidate inputs and an actual finite execution budget have not been finalized. Passing a structural review does not automatically authorize or execute a solver.

These safeguards cannot prove that an idea is new. The relevant literature, code and previous results must actually be read and compared against the proposed decision and changed inputs. Reproduction is worthwhile when it closes a specific independent-validation or reproducibility gap; it must stay labeled reproduction. Reopening a completed test merely to produce a higher run count, nicer animation or a preferred result is not justified. A changed run budget needs a written reason before execution, not an unseen extension until a favorable outcome appears.

## Verification and publication scope
Tests check event coverage, source hashes, latest scientific versus interface status, goal dependencies, missing-input/run-budget failures and unchanged-repeat rejection. Actual installed-Edge checks will inspect selectable markers, the show-tooling switch, goal links, prior-work filtering, the shared homepage graph and a narrow viewport. A local pass and a deployed exact-revision pass are distinct records. No signed-in profile, weakened browser security or unreviewed contributor execution is required.

No existing scientific dataset, model-power result, particle trajectory, equilibrium field or native Unreal executable is changed. No new physics/transport optimization or physical experiment is conducted for this graph. Canonical outputs and the original source-specific rights remain intact; only reviewed summaries and links are added.
